# [一次性] 下载→归位闭环真实环境验证清单

> 用途：把“还没证明”的部分压成最小可执行验证面板。  
> 适用主线：`下载完成 → 本地转移 → 局部刷新 → 自动归位 → confirm/execute → 回收站/持久化`  
> 对应 TODO：`optimization-stabilization-todo.md`

---

## 执行原则

- 每次只验证一个场景，不混跑
- 每个场景只选一个最小样本，不追求覆盖面
- 先记录前置状态，再执行，再记录结果
- 出现异常时先保留现场，不立即手工清理

---

## 场景 A：真实 NAS `organize execute` 小样本

### 目标

- 证明真实 NAS 上 `dry-run -> execute` 能完成落盘
- 证明落盘后目录结构、NFO、封箱结果符合当前隔离层预期

### 前置条件

- 准备 1 个最小下载样本：
  - 推荐：单季单集或单电影
  - 要求：目标库中已有 1 份旧资源，能稳定触发冲突或替换链路
- 明确本次验证对象：
  - 下载任务 ID
  - `save_path`
  - 对应媒体库目标目录
- 确认 qB / Alist / 媒体库路径都指向真实环境，不使用临时假目录

### 步骤

1. 触发一次真实下载，等待任务进入 `completed`
2. 调用 `/organize/dry-run`
3. 保存返回的：
   - `old_tree`
   - `new_tree`
   - `plan_tree`
   - `coexist_pairs`
4. 调用 `/organize/execute` 或通过确认链进入 execute
5. 记录执行后目录状态：
   - 新文件是否落到目标目录
   - 旧文件是否进入回收站或备份目录
   - NFO / 海报 / season 级文件是否符合预期

### 关键观测点

- `action_plan` 是否和 `dry-run` 一致
- `save_path` 与真实落盘目录是否一致
- 旧资源处理方式是否与选择动作一致：
  - 替换：进入回收站
  - 共处：进入 `[旧资源备份]`
- 目录级 `tvshow.nfo` 未被误处理

### 通过判据

- 接口返回成功
- 目标目录存在预期新文件
- 旧文件进入预期位置
- 无“落盘到了错误目录 / 执行后目录空了 / NFO 被误删”这类主链路错误

### 失败判据

- `dry-run` 与 `execute` 使用了不同目录
- 新文件未落盘或落错位置
- 旧文件处理与用户动作不一致
- 目录级关键元数据被误删

## 场景 B：真实 `confirm_replace + execute` 交叠时序

### 目标

- 证明真实线程下自动归位、用户确认、落盘执行不会互相踩踏
- 观察 `awaiting_confirm -> archived` 的时序是否稳定

### 前置条件

- 准备 1 个必定触发冲突的样本
- 确认任务会进入 `awaiting_confirm`
- 能同时观察：
  - 下载任务状态变化
  - 回收站变化
  - 目标目录变化

### 步骤

1. 触发真实下载并等待自动归位进入 `awaiting_confirm`
2. 记录此时：
   - 任务状态
   - `coexist_pairs`
   - 目标目录旧文件状态
3. 在确认窗口期执行 `confirm_replace`
4. 观察直到任务进入最终态
5. 记录是否出现重复执行、重复回收、状态回跳

### 关键观测点

- `confirm_replace` 是否只执行一次
- `_execute_plan` 是否只执行一次
- 旧资源是否只被回收一次
- 最终状态是否稳定停在 `archived`
- 是否出现：
  - `awaiting_confirm -> archived -> awaiting_confirm`
  - 重复回收
  - 同一文件重复执行

### 通过判据

- 状态单向收口到 `archived`
- 回收站里没有同一路径的重复动作
- 目标目录无重复副本或半执行残留

### 失败判据

- 状态回跳
- 重复回收 / 重复执行
- 执行成功但任务状态未收口

## 场景 C：真实 qB / Alist 异常小样本

### 目标

- 用最小真实样本验证下载器在异常返回、超时、短时抖动下不会把主链路拉坏

### 前置条件

- qB 和 Alist 至少各准备 1 个可观察任务
- 能制造或捕获 1 次轻量异常：
  - 短时断连
  - 接口超时
  - 返回空列表 / 状态未命中

### 步骤

1. 选择 qB 样本任务，记录异常前状态
2. 制造或等待 1 次轻量异常，执行一次 `sync_progress`
3. 记录任务是否落到 `unknown` / `lost` / 保持 `downloading`
4. 对 Alist 重复同样流程
5. 异常解除后，再观察一次状态是否能继续收口

### 关键观测点

- `unknown` 是否只作为短时回退，不误触发归位
- `lost` 是否只在确实查不到任务时出现
- 异常期间不会误发订阅完成 / 自动归位 / execute

### 通过判据

- 异常期间主链路没有误收口
- 异常解除后任务还能继续推进或保持可恢复状态

### 失败判据

- 异常时误触发 `completed` / 自动归位 / 订阅完成
- 状态直接错误收口且无法恢复

## 记录模板

每次真实验证至少记录以下字段：

- 日期
- 场景编号：`A` / `B` / `C`
- 样本类型：电影 / 单集 / 季包
- 下载通道：`qb` / `alist`
- 任务 ID
- 预期结果
- 实际结果
- 是否通过
- 异常现象
- 是否需要回写 TODO / worklog / devlog

## 收口规则

- 场景 A/B/C 各至少通过 1 个最小样本，才算这条主线进入“真实环境已开证”
- 若任一场景失败，先回写本文件和 worklog，再决定是否恢复代码修改
