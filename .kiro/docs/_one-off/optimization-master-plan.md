# [一次性] 项目整体优化基本盘

> 目标：不是继续堆新功能，而是在不破坏现有核心能力的前提下，系统性优化项目的结构、代码、功能与体验，建立后续长期迭代的稳定底座。
> 适用范围：整个项目，不局限于订阅或 AI。
> 最后更新：2026-04-23

---

## 一、文档定位

这不是某个子功能的设计文档，而是整个项目后续优化的“基本盘”。

它解决 4 个问题：

1. 项目真正的核心主链路是什么
2. 后续优化应该先改哪里、后改哪里
3. 怎么在优化结构和代码时尽量不引入新 bug
4. 哪些能力应该沉淀成长期资产（模块 / Skill / 工程规范）

## 当前阶段覆盖协议：收口校准阶段

当前阶段：功能已基本完成，进入低风险收口、稳定主链路、建立安全底座阶段。

本节优先于本文后续路线图中的架构建议。后续路线图只作为方向，不作为立即执行清单。

### 阶段总原则

当前阶段排序：

```text
稳定 > 正确 > 可验证 > 优雅
```

Codex 角色定位为：保守型维护者（Stability Guardian）。

成功标准不是代码更优雅，而是可以证明主链路没有被破坏。

禁止：

- 主动扩展功能
- 主动进行架构升级
- 主动进行 Skill / MCP 抽象设计
- 为未来扩展提前设计结构
- 主动修改前端 UI、样式、design token

只允许：

- 收口已有结构
- 降低耦合
- 提升可验证性
- 记录未来资产候选，但不实现资产化

### 单轮改动边界

每一轮只允许做一种类型的改造：

- 结构收口
- 类型补强
- 测试补强
- 文档 / TODO 补强

当前阶段默认禁止业务逻辑修改。

严禁混合改动：

- 结构调整 + 业务逻辑修改
- 重构 + 修 bug
- 抽象 + 行为优化
- 顺手统一行为 / 接口 / 字段

### 行为保护机制

代码能运行不等于行为没坏。任何代码收口前，至少完成一项：

- 记录输入输出
- 记录排序 / 过滤结果
- 记录关键路径
- 运行现有测试

修改后必须说明：

- 是否行为等价
- 输出 / 排序 / 过滤是否一致
- 是否存在行为漂移风险
- 哪些风险无法证明

无法证明行为等价时，必须停止修改。

### 默认不可动区

以下链路默认不可主动修改：

- naming 规则
- search filter / sort
- organize executor
- file_relocator 冲突探测
- TV 映射
- 下载 → 归位闭环

如任务确实影响这些区域，必须单独说明、单独验证，并把结论写入本轮报告。

### DTO 与资产化降级

DTO 允许逐步引入，但禁止一次性全量迁移。

当前阶段只识别资产，不实现资产：

- 重复实现 + 行为稳定 + 不改变接口 + 可完全回滚时，才允许做局部抽象
- 否则只记录为“未来资产候选”

### 本阶段输出报告格式

每轮交付必须使用以下格式：

```text
【本轮目标】
【涉及文件】
【改动性质】结构收口 / 类型补强 / 测试补强 / 文档补强
【已完成】
【未触碰】
【验证结果】
- 静态检查
- 搜索检查
- 测试结果
【未能证明的风险】
【风险检查】
- 是否改业务逻辑：是/否
- 是否改接口字段：是/否
- 是否改路由行为：是/否
- 是否影响主链路：是/否
【结论】安全 / 部分验证 / 有风险
```

### 停止条件

出现以下任一情况必须停止：

- 无法证明行为等价
- 测试不足
- 影响高风险链路
- 出现连锁修改
- 需要修改接口 / 路由

当前阶段详细执行清单见：`optimization-stabilization-todo.md`。

## 二、项目核心判断

### 2.1 产品真正的主轴

从整个项目看，真正的核心不是订阅系统，也不是 AI 辅助，而是下面 4 条主链路：

1. **媒体识别与命名链路**
2. **搜索、匹配与筛选链路**
3. **刮削、整理与归位链路**
4. **下载、替换与结果闭环链路**

订阅与 AI 都属于建立在这 4 条主链路之上的增强层：

- **订阅** = 自动化搜索与下载编排层
- **AI** = 智能增强与疑难兜底层

如果核心主链路不稳，继续扩订阅和 AI 只会放大复杂度、放大隐式依赖、放大回归风险。

### 2.2 当前阶段判断

项目已经从“功能原型期”进入“能力成型期”：

- 核心功能已基本齐全
- 技术债开始集中暴露
- 重复逻辑开始变多
- 文档、skills、知识资产已经形成雏形
- 如果不做系统性收口，后续迭代成本会持续上升

因此，接下来的重点应该从“继续扩功能”切换为：

**收口核心链路 → 分层架构 → 沉淀资产 → 再继续扩展**

## 三、整体优化目标

后续优化必须同时满足 4 个目标：

### 3.1 结构优化

- 减少模块耦合
- 减少 shared.py 式隐式依赖
- 让主链路边界清晰
- 让路由层变薄，业务层变稳

### 3.2 代码优化

- 消灭重复实现
- 压缩巨型函数 / 巨型模块
- 建立统一规则中心
- 建立统一数据模型和状态机

### 3.3 功能优化

- 优先提升核心流程的准确率、稳定性和可预测性
- 先补“成功率”和“一致性”，再补“新能力”
- 避免一个流程在不同入口行为不一致

### 3.4 体验优化

- 让用户关键链路更顺滑
- 增强结果可信度反馈
- 优化局部状态同步，减少“操作成功但界面没跟上”的割裂感

## 五、最该优先优化的 6 个核心对象

### 5.1 名称链路

这是全项目最关键的底层资产。

范围包括：

- 文件名解析
- clean name
- shadow name
- cn / en / original 多语言名
- 名称可信度优先级
- 从 NFO / TMDB / 豆瓣 / Bangumi 的名称回写

问题：

- 逻辑散落在多个模块
- 名称来源优先级虽已形成，但写入点仍然分散
- 不同链路对“标准名”的理解还不完全统一

结论：

**名称链路必须作为第一优先级统一域。**

### 5.2 搜索链路

范围包括：

- 多语言搜索词构造
- 多源搜索调度
- enrich_result
- smart filter
- match / filter / sort
- 手动搜索 / SSE / 订阅直搜共用内核

问题：

- 多入口重复实现仍然明显
- 规则已有沉淀，但工程边界还不够统一
- route、service、scheduler 之间职责仍有重叠

结论：

**搜索链路必须作为第二优先级统一域。**

### 5.3 刮削链路

范围包括：

- 候选搜索
- movie/tv/episode NFO
- TV 确权
- 分集映射
- 海报 / fanart
- 批量刮削

问题：

- scraper.py 职责过重
- 候选匹配、TV 映射、NFO 写入、海报下载仍然耦合偏紧

结论：

**刮削链路必须模块化。**

### 5.4 整理链路

范围包括：

- analyze
- wrap
- archive
- rename
- reorganize seasons
- organize/full
- rollback

问题：

- 分析和执行缠绕
- dry-run 与 execute 的一致性维护成本高
- 一键整理逻辑散在多个入口

结论：

**整理链路要强制拆成分析层与执行层。**

### 5.5 下载替换链路

范围包括：

- 下载任务状态机
- 完成检测
- 局部刷新
- file_relocator
- 冲突探测
- 替换 / 共存 / 回收站

问题：

- 下载模块和整理模块已经开始互相侵入
- 任务成功不等于闭环完成，链路边界不够清晰

结论：

**下载链路要变成独立的闭环域，而不是杂糅在 route 和 manager 中。**

### 5.6 前端状态链路

范围包括：

- useLibrary
- DetailDrawer
- SearchModal
- DownloadManagerPanel
- useSubscriptions
- 页面刷新与局部状态同步

问题：

- hook 逐步膨胀
- 状态变更多源
- 局部刷新依赖较多隐式逻辑

结论：

**前端要逐步转向 view-model 分层。**

## 阶段 A：底座收口期

目标：先减少后续改动引入新 bug 的概率  
周期建议：1-2 周

### A1. 建立统一规则中心

把散落在各模块中的规则收拢到统一位置。

优先收拢：

- 视频扩展名
- 忽略目录
- 搜索源定义
- 名称来源优先级
- 质量阈值
- 特别篇 / 季目录 / 特殊目录规则
- 统一状态枚举

建议新增：

```text
backend/core/constants.py
backend/core/policies/
```

当前进度：

- 2026-04-23：已建立 `backend/core/constants.py`，先收口视频扩展名、字幕扩展名、标准 NFO 名、同名刮削后缀等低风险静态规则；第一轮只迁移 analyzer / organizer / renamer / file_relocator / nfo_handler 的重复引用。

收益：

- 降低规则不一致导致的回归
- 新增源 / 新增流程时不用到处复制逻辑

### A2. 建立统一 DTO 与类型边界

当前很多跨模块通信仍然依赖 dict，长期风险高。

优先建立：

- SearchRequest / SearchResult
- ScrapePlan / ScrapeResult
- OrganizePlan / OrganizeResult
- RelocatePlan / RelocateResult
- MediaNameBundle
- VideoEntry / FolderNode

收益：

- 降低隐式字段依赖
- 提升测试稳定性
- 降低前后端字段漂移

### A3. 降级 shared.py

目标不是删除 shared.py，而是限制其职责。

shared.py 只允许保留：

- 单例工厂
- 配置装配
- 生命周期启动
- 容器入口

禁止继续往 shared.py 加业务 helper。

收益：

- 控制耦合继续扩散
- 为后续按域拆分铺路

## 七、哪些部分先不该继续扩

在阶段 A/B 结束前，不建议继续大幅扩展以下方向：

### 7.1 不优先继续扩 AI 场景

原因：

- AI 还处在“场景型增强”阶段
- 底层名称 / 搜索 / 刮削 / 整理链路还没彻底收口
- 继续加 AI 容易把边界搞得更散

原则：

- 保持现有一期能力稳定
- 先做 scene 协议化和接入规范化

### 7.2 不优先继续扩订阅复杂度

原因：

- 订阅系统已经从功能模块长成子系统
- 现在更需要边界收口，而不是再加更多策略

原则：

- 新增源可以继续，但不继续扩复杂规则
- 优先把数据、调度、查询、通知、日志边界拆清楚

## 八、如何尽量避免引入新 bug

这是整个优化过程中的最高优先级约束。

### 8.1 只做“收口式重构”

每一轮只允许做一种类型的改造：

- 要么拆边界
- 要么抽公共层
- 要么统一模型
- 要么补回归测试

禁止一轮里同时：

- 改结构
- 改交互
- 改业务规则
- 加新能力

### 8.2 先冻结主链路行为

在重构前先固定下面 4 条行为基线：

1. 搜索结果排序 / 过滤行为
2. TV 刮削映射行为
3. organize dry-run / execute 行为
4. 下载完成到归位替换行为

先形成回归快照，再做内部重构。

### 8.3 优先补“行为保护测试”

比新增单元测试更重要的是新增链路测试：

- 搜索链端到端回归测试
- TV 刮削映射回归测试
- organize dry-run 与 execute 一致性测试
- 下载完成到归位的闭环测试
- 名称优先级覆盖测试
- 前端关键交互 smoke test

### 8.4 建立“不可动区”

建议内部明确以下区域属于高风险改动区：

- naming 规则
- smart filter 规则
- organize executor
- file_relocator 核心冲突探测

任何改动都必须先补回归测试。

## 九、长期资产化建议

优化不是只为了当前项目，也要顺便把真正成熟的能力抽成资产。

### 9.1 最适合先沉淀成业务 Skill 的

优先级排序：

1. 文件名解析 + 清洗名 + 影子名
2. 多语言搜索词分发 + 智能过滤
3. TV 刮削确权与分集映射
4. 归位冲突探测
5. 订阅调度器

### 9.2 最适合沉淀成通用工程 Skill 的

优先级排序：

1. 任务状态机
2. 两段式提交
3. SSE 流式通信
4. 优先级保护写入
5. 持久化缓存

### 9.3 最适合做独立开源模块的

优先考虑两个方向：

#### 模块 A：媒体命名与分集解析内核

特点：

- 输入输出清晰
- 依赖少
- 与 UI / 下载器 / 配置弱耦合

#### 模块 B：混合订阅调度器

特点：

- RSS + 直搜双通道
- 适用于影视、漫画、资源监控等项目

## 十、优先级最高的 Top 3 改造建议

### 1. 统一“名称链 + 搜索链”

原因：

- 这是整个项目复用最广、出错影响最大的底座
- 搜索、刮削、整理、发现页、订阅都依赖它

### 2. 拆“分析 / 执行 / 文件事务”

原因：

- 这是降低回归风险的关键
- 任何会改文件的能力最终都会经过这条链

### 3. 前端状态模型分层

原因：

- 后续体验优化和功能增强都会压在前端状态同步上
- 现在不拆，后面 Detail / Search / Download / Subscribe 会越来越难改

## 十一、推荐执行顺序

> 收口校准阶段覆盖说明：以下四周路线是中期方向，不再作为当前立即执行计划。当前阶段先执行 `optimization-stabilization-todo.md`，完成行为基线与低风险收口准入后，再进入本节的阶段 A/B/C/D。

### 第一周

只做收口，不加新功能；在收口校准阶段优先转化为“行为基线 + 重复点盘点 + 低风险收口准入”。

目标：

- 统一规则中心设计
- shared.py 迁移清单（只盘点，不迁移）
- naming 域边界草图（只记录，不建域）
- search 域边界草图（只记录，不建域）

### 第二周

目标：

- 先建立搜索行为基线，再判断是否允许拆 routes/search.py
- naming 域初版降级为命名链路 DTO / 规则候选盘点
- 搜索域初版降级为搜索入口重复点清单
- 基础 DTO 只允许局部补强，不做全量迁移

### 第三周

目标：

- organize 拆成 analyze / executor / orchestrator
- 文件事务层初版
- 下载替换链路边界梳理

### 第四周

目标：

- 前端 hook 分层第一轮
- 关键链路行为测试补齐
- 技能资产整理与目录对齐

## 十二、文档与代码的对齐原则

从现在开始，`.kiro/docs` 不应只是说明书，而应成为工程契约层。

每个核心设计文档建议统一补以下字段：

- 当前状态
- 代码入口
- 已落地文件
- 未落地项
- 依赖前置项
- 风险点
- 下一阶段目标

这样文档才能直接指导开发和重构，而不是只做回顾材料。

## 十三、最终结论

当前项目最重要的，不是继续扩订阅，也不是继续扩 AI。

最重要的是：

1. 先把 **命名、搜索、刮削、整理、下载** 这 5 个核心底座收稳
2. 再让订阅和 AI 作为增强层稳定挂载
3. 最后再进入下一轮功能扩展

一句话总结：

**先把“媒体库主引擎”打磨成稳定平台，再继续扩上层能力。**

这就是后续所有优化工作的基本盘。
