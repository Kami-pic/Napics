# NAS Video Upgrader — 产品全景总结

> 本文档用于与外部 AI 讨论产品方向（商业化 vs 开源），概述产品现状、功能、技术架构和关键决策点。

---

## 一、产品定位

**一句话**：面向个人 NAS 用户的一站式影视媒体库管理工具。

**核心价值**：把散乱的视频文件变成有组织、有元数据、可持续升级的个人影视库。用户不需要懂技术细节，通过 Web UI 完成从"发现新片→搜索资源→下载→整理入库→持续升级"的完整闭环。

**当前用户画像**：
- 拥有群晖/威联通等 NAS 的影视爱好者
- 有一定动手能力（能配置 qBittorrent、Prowlarr 等工具）
- 追求高质量收藏（关注分辨率、音轨、字幕）
- 目前仅作者本人使用，运行在 Windows + SMB 挂载 NAS 的环境

**对标产品**：
- Radarr/Sonarr（自动化下载管理，但不管整理和刮削）
- tinyMediaManager（刮削工具，但不管搜索下载）
- Jellyfin/Emby/Plex（播放器+刮削，但不管资源获取）
- 本产品的差异化：**全链路打通**，从发现→搜索→下载→整理→刮削→升级，一个工具搞定

## 二、功能模块清单（用户视角）

### 2.1 媒体库管理（核心）
- **扫描**：扫描 NAS 指定目录，提取视频元数据（文件名/大小/编码/分辨率/时长）
- **树形浏览**：以文件夹树形式展示媒体库，支持展开/折叠/搜索
- **智能分类**：自动识别电影/剧集/系列/合集/季/混合类型
- **质量评分**：100 分制（分辨率+来源+音频+编码+字幕），全局统一基准

### 2.2 刮削（元数据获取）
- **多源刮削**：TMDB / 豆瓣 / Bangumi 三源
- **自动匹配**：智能匹配候选，支持 AI 辅助选择
- **NFO 生成**：标准 Kodi/Jellyfin 兼容的 NFO 文件
- **海报下载**：自动下载封面海报
- **批量刮削**：一键刮削整个目录

### 2.3 整理（文件组织）
- **三段式流水线**：分析→生成 Action Plan→执行
- **标准化目录结构**：自动创建季目录、重命名文件（S01E01 格式）
- **影子名**：为中文文件夹生成英文别名，方便 Jellyfin 识别
- **操作快照**：每次整理前自动快照，支持一键回滚
- **流式进度**：SSE 实时推送整理进度

### 2.4 搜索（资源发现）
- **BT/磁力搜索**：
  - Prowlarr 聚合搜索（主力）
  - 12 个直搜源（Bitsearch/磁力熊/XL720/Nyaa/蜜柑/YTS/LimeTorrents/ACG.RIP/Bangumi Moe/EZTV/动漫花园/1337x）
  - SSE 全源并行，逐个推送结果
  - 智能过滤（枪版/低匹配/死种/跨语言不匹配/标题占比过低）
  - 多语言搜索词自动构造 + 回退链
- **网盘搜索**：
  - 6 个源（pansearch/pansou/gogopanso/github/rrdynb/ddys）
  - 支持夸克/阿里/百度/115/PikPak 网盘链接提取
- **搜索匹配通用能力层**：
  - L1 文本处理（繁简转换/语言检测/分词）
  - L2 匹配评分（快速筛选+精细排名）
  - L3 数据过滤（include/exclude/阈值/去重/流水线）
  - L4 结果排序（多级排序+权重排序）

### 2.5 下载管理
- **qBittorrent 集成**：直接推送磁力链接/种子
- **Alist 网盘管理**：云端下载→本地同步两阶段
- **归位替换**：下载完成后自动推演归位方案，支持确认/归档/取消
- **回收站**：删除的文件进回收站（30 天），可恢复
- **种子黑名单**：标记不良种子，后续搜索自动排除

### 2.6 发现推荐
- **三源融合**：豆瓣热榜 + TMDB Trending + Bangumi 日历
- **探索筛选**：按风格/地区/年代/评分/排序多维筛选
- **本地感知**：自动标记"已有"/"可升级"，避免重复下载
- **详情面板**：点击卡片展开详情，一键搜索/下载/订阅
- **TMDB 英文名缓存**：持久化缓存，加速多语言搜索

### 2.7 订阅系统
- **RSS + 直搜双通道**：
  - RSS 高频轮询（5 分钟）：Prowlarr/蜜柑/Nyaa/EZTV/动漫花园/ACG.RIP/Bangumi Moe/YTS
  - 直搜低频补充（4 小时）：磁力熊/XL720/Bitsearch
- **两种模式**：追更（follow）/ 洗版升级（upgrade）
- **自动下载**：匹配到资源自动推送下载
- **洗版机制**：持续搜索更高质量版本，自动替换
- **日历视图**：TMDB/Bangumi 放送日历
- **搜索日志 + 通知**：记录每次搜索结果，下载完成通知

### 2.8 AI 集成（一期）
- **AI 文件名解析**：复杂文件名用 LLM 提取集号
- **AI 刮削候选匹配**：多候选时用 LLM 选择最佳匹配
- **AI 媒体库诊断**：分析目录结构问题并给出建议
- **多服务商支持**：火山引擎豆包 / DeepSeek / 任意 OpenAI 兼容
- **全局开关 + 场景级开关**：可完全关闭，关闭时静默降级

### 2.9 季集完整性检测
- 从 TMDB 获取完整季/集结构，与本地文件做差集
- 可视化进度条显示缺集情况
- 自动刷新（媒体库变更时后台更新）

### 2.10 批量操作
- 批量升级低质量视频（搜索+下载+替换）
- 批量刮削
- 批量整理
- 批量删除（进回收站）

## 三、技术架构

### 3.1 技术栈
| 层 | 技术 |
|---|---|
| 后端 | Python 3 + FastAPI + Uvicorn |
| 前端 | Next.js 16 + React 19 + Tailwind CSS 4 |
| 数据存储 | JSON 文件（无数据库） |
| 外部依赖 | TMDB API / Prowlarr / qBittorrent / Alist / 豆瓣 / Bangumi |

### 3.2 后端架构（分层）
```
入口层        main.py（薄壳，只注册路由）
路由层        routes/*（13 个路由文件，按业务域拆分）
业务逻辑层    organizer / renamer / scraper / download_manager / subscriber 等
数据获取层    tmdb_client / douban_client / searcher / 各爬虫
基础设施层    config_manager / downloader / quality_parser / recycle_bin
共享层        shared.py（单例初始化 + 依赖注入）
```

### 3.3 前端架构
```
app/            页面路由（首页 + 管理页）
components/     UI 组件（按领域分组：media/search/detail/download/settings/ai）
hooks/          自定义 hooks
lib/            工具函数 + API 模块
types/          TypeScript 类型定义
```

### 3.4 数据持久化
- `media_library.json` — 媒体库树形结构（核心数据）
- `config.json` — 用户配置
- `download_tasks.json` — 下载任务队列
- `subscriptions.json` — 订阅列表
- `completeness_cache.json` — 季集完整性缓存
- `scrape_cache/` — 刮削缓存目录
- `organize_snapshots/` — 整理操作快照（用于回滚）

### 3.5 代码规模（估算）
- 后端核心模块：~50 个 .py 文件
- BT 直搜源爬虫：12 个
- 网盘爬虫：8 个
- RSS 源：8 个
- 测试文件：~80 个 test_*.py
- 前端组件：~40+ 个 .tsx 文件
- 一次性脚本（调试/迁移）：~80 个 _*.py（不属于核心代码）

## 四、当前状态

### 4.1 已完成且稳定的功能
- ✅ 媒体库扫描/浏览/树形展示
- ✅ 多源刮削（TMDB/豆瓣/Bangumi）
- ✅ 智能整理流水线 V3（分类+重命名+结构化）
- ✅ BT/磁力全源并行搜索 + 智能过滤
- ✅ 网盘搜索
- ✅ 下载管理（qB + Alist）+ 归位替换
- ✅ 发现推荐（三源融合+探索筛选+本地感知）
- ✅ 订阅系统（RSS+直搜+洗版+日历+通知）
- ✅ 季集完整性检测
- ✅ AI 集成一期
- ✅ 清洗名系统（多语言名称处理）
- ✅ 搜索匹配通用能力层 L1-L4
- ✅ 多语言搜索词自动构造

### 4.2 已知问题/技术债
- 下载管理的 sync_progress 没有后台定时调用
- qB 同步会把所有种子导入为新任务（删除的失败任务重启后复活）
- 前端"已完成"和"待整理"Tab 从用户角度重复
- 数据持久化用 JSON 文件，无并发安全保障（单用户场景够用）
- 部分爬虫源不稳定（ACG.RIP 被墙、LimeTorrents TLS 报错，已默认禁用）
- 配置修改后部分组件需重启后端生效

### 4.3 强依赖外部服务
- **必须**：TMDB API（刮削+完整性检测+英文名）、qBittorrent（BT 下载）
- **推荐**：Prowlarr（BT 聚合搜索）、Alist（网盘管理）
- **可选**：豆瓣/Bangumi（补充刮削源+推荐）、AI 服务商（增强功能）
- **网络**：TMDB/部分 BT 源需要代理

## 五、如果要给更多人用，需要考虑的关键问题

### 5.1 部署和环境
- 当前：Windows + SMB 挂载，localhost 访问
- 需要：Docker 化？Linux 支持？远程访问？多用户？

### 5.2 配置复杂度
- 当前需要用户自行配置：Prowlarr、qBittorrent、Alist、TMDB API Key、代理
- 这些外部依赖是否可以简化？哪些是必须的？

### 5.3 数据安全
- JSON 文件无事务保障，多用户/多实例场景有风险
- 是否需要迁移到数据库？

### 5.4 功能取舍
- 哪些功能是核心差异化（必须保留）？
- 哪些功能是个人定制（可以删除或做成插件）？
- 哪些功能有法律风险（搜索/下载相关）？

### 5.5 商业化 vs 开源的考量维度
| 维度 | 商业化 | 开源 |
|------|--------|------|
| 用户获取 | 需要营销，门槛高 | 社区传播，门槛低 |
| 收入模式 | 订阅/买断/增值服务 | 捐赠/Pro版/托管服务 |
| 维护压力 | 必须持续投入 | 社区贡献分担 |
| 法律风险 | 搜索/下载功能敏感 | 开源可声明"仅供学习" |
| 竞品壁垒 | 代码私有 | 可被 fork |
| 外部服务依赖 | 需要稳定的 API | 社区可自行适配 |
| 用户支持 | 需要客服 | 社区互助 |

### 5.6 如果开源
- 需要清理：个人配置、API Key、NAS 路径、一次性脚本
- 需要补充：安装文档、Docker Compose、配置向导
- 需要考虑：License 选择、贡献指南、Issue 模板
- 爬虫/搜索源的合规性（是否需要做成插件/可选模块）

### 5.7 如果商业化
- 需要：用户系统、付费逻辑、部署方案（SaaS vs 本地）
- 需要：稳定性保障、错误监控、用户反馈渠道
- 需要考虑：搜索/下载功能的法律合规
- 差异化定位：和 Radarr/Sonarr/tinyMediaManager 的区别在哪

## 六、功能模块依赖关系图

```
[发现推荐] ──→ [搜索] ──→ [下载管理] ──→ [归位替换] ──→ [媒体库]
     ↑                                                        ↓
[订阅系统] ──→ [搜索] ──→ [下载管理] ──→ [归位替换]      [刮削]
                                                              ↓
                                                         [整理流水线]
                                                              ↓
                                                         [季集完整性]
```

核心数据流：**媒体库 JSON** 是中心，所有模块围绕它读写。
