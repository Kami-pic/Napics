# AI 行为准则

---

## 1. 沟通规范
- 所有回复、注释、思考过程必须 100% 中文
- 用户反馈"页面没变化"直接查 UI 渲染层，不要建议清缓存（用户每次都强制刷新）
- 出错时不要道歉，直接修复；代码暂时不完整时加 TODO 注释标记
- 方案讨论时独立思考，批判性审视用户想法，给出自己的判断，不迎合式附和
- **关键不确定时先确认**：涉及实现方向、数据安全或用户可见行为时必须询问
- **多方案时主动列权衡**：如果存在 ≥2 种实现路径，列出各自优缺点，不要只给一个

## 2. 最小改动原则（硬性要求）
> 来源：Karpathy LLM 编码观察 — "LLM 喜欢过度复杂化代码、膨胀抽象、不清理死代码"
- **只做被要求的事**：不加没要求的功能、不加投机性的抽象、不加不可能场景的错误处理
- **手术式修改**：只改必须改的，不顺手"改进"相邻代码、注释、格式。但如果相邻代码严重违反 code-style.md（如路由层含 50+ 行业务逻辑），应一并拆分
- **匹配现有风格**：即使你觉得可以更好，也跟着项目现有写法走
- **自己的垃圾自己收**：你的改动产生的孤立 import/变量/函数要清理；已有的死代码提一嘴但不删，错误要记todo
- **文档也是最小改动**：编辑已有文件用 `strReplace` 局部替换，禁止 `fsWrite` 重写整文件（大文件重写易触发 aborted 反复重试）
- **检验标准**：每一行改动都应该能追溯到用户的请求。追溯不到的，删掉

## 3. 自测与验证（硬性要求）
- 写完代码必须自测，不允许"没报错就算完成"
- 后端写 test_*.py 并运行；前端用 getDiagnostics 检查，不能只靠构建通过
- **测试沙盒**：`backend/sandbox_real/` 是从真实 NAS 媒体库复制的目录结构（空文件），涉及文件整理、匹配、刮削、搜索等功能时，优先用沙盒数据做集成测试
- **前后端必须同时验证**：改了后端必须检查前端调用是否适配（getDiagnostics + 构建）；改了前端必须确认后端接口没变。不允许只验一端
- **交付必须闭环验证**：新增的函数/接口/组件，必须有调用方；新增的调用方，必须被入口页面引用。验证方法：从用户可见的入口出发，追踪到新增代码，确认链路完整。"编译通过"只是最低门槛，"用户能触发并看到结果"才是完成标准
- **里程碑交付前逐条核对设计文档**：拿设计文档的"改动范围"逐条对账实际交付物，未完成的标记 TODO 并明确告知用户，不允许默认跳过
- 里程碑完成后跑完整测试（后端 pytest，前端 vitest）
- 测试失败必须实证，禁止猜测归因
- **测试产出的所有问题必须处理**：error、failure、warning 都不能跳过。能当场修的立即修；不属于当前任务的记录到对应 TODO 文件的"技术债务"区域，标注来源和复现方式。"测试全绿"是交付标准，不是"跑了就行"

## 4. 多步任务先列计划（硬性要求）
> 来源：Karpathy — "给 LLM 成功标准让它自己循环，比告诉它做什么更有效"
- 超过 3 个文件的改动，或涉及状态机/流程编排的改动，先列出步骤计划，每步带验证点：`[步骤] → 验证: [检查方式]`
- 把命令式任务转化为可验证目标：不是"加个验证"，而是"写测试覆盖非法输入，然后让测试通过"
- 计划中必须包含前端和后端的验证步骤，不允许只列一端

## 5. 调试排错（硬性要求）
- **最多猜 1 次**：修复 bug 可以快速尝试一次，无效立即加日志做科学排查，定位根因后再修
- 前端检查顺序：Console → Network → 组件重渲染 → CSS；后端：请求日志 → 返回数据 → 异常堆栈 → 缓存

## 6. 高危操作
- 全量数据操作/脚本执行必须等用户确认；批量操作先测 5 个样本再全量

## 7. 知识库维护
- devlog / docs 可以按规则自动写；project-memory / 领域 knowledge 只有跨轮长期有效时才写，且写前确认。
- **写入判断**：这条信息换个人接手还需要知道吗？
  - 写：业务规则、API 约定、匹配算法逻辑、数据格式、踩坑经验
  - 不写：bug 调试过程、临时 workaround、版本号、实现细节（看代码）、通用编程知识
  - 跨模块的写 project-memory.md，特定领域的写对应 knowledge 文件
- **状态覆写**：更新时直接修改旧内容，不保留矛盾的历史版本
- **同步检查**：更新 steering 或 knowledge 文件后，检查根目录 AI_GUIDE.md 是否需要同步

## 8. 代码提交
- 里程碑完成后提交，提交前更新 TODO + 相关 knowledge 文件 + devlog.md 归档，用户确认后再 push
- commit message 中文多行：第一行 `类型: 描述`，body 写变更要点和踩坑经验
- 提交前核对文件列表，严禁提交 node_modules/venv/dist/__pycache__ 等

## 9. 项目推进
- 日常迭代用 TODO 驱动（`.kiro/docs/*-todo.md`），不主动创建新 spec

## 10. 会话接力
- 修改后端 Python 或前端组件代码前，先读 project-memory.md 获取领域索引和核心红线
- 按需深入读取对应的 knowledge 文件（memory 中有索引）
- 纯样式调整、依赖升级等不涉及业务数据流的改动可跳过
