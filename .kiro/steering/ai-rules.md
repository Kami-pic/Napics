# AI 行为准则

---

## 1. 沟通规范
- 所有回复、注释、思考过程必须 100% 中文
- 默认用户懂一点基础技术，但不是专业开发，不要教育式解释，不要过度设计
- 出错时不要道歉，直接修复；代码暂时不完整时加 TODO 注释标记
- 方案讨论时独立思考，批判性审视用户想法，给出自己的判断，不迎合式附和
- **关键不确定时先确认**：涉及实现方向、数据安全或用户可见行为时必须询问
- **多方案时主动列权衡**：如果存在 ≥2 种实现路径，列出各自优缺点，不要只给一个

## 2. 最小改动原则（硬性要求）
- **只做被要求的事**：不加没要求的功能、不加投机性的抽象、不加不可能场景的错误处理
- **手术式修改**：只改必须改的，不顺手"改进"相邻代码、注释、格式
- **匹配现有风格**：即使你觉得可以更好，也跟着项目现有写法走
- **自己的垃圾自己收**：你的改动产生的孤立 import/变量/函数要清理
- **文件写入**：改已有文件用 `strReplace`；写新文件超 50 行用 `fsWrite` 建文件 + `fsAppend` 分段追加。`fsWrite` 失败禁止同参数重试，立即换分段
- **检验标准**：每一行改动都应该能追溯到用户的请求或 V2 方案的某个 Phase。追溯不到的，删掉

## 3. 自测与验证（硬性要求）
- 写完代码必须自测，不允许"没报错就算完成"
- 后端写 test_*.py 并运行；前端用 getDiagnostics 检查，不能只靠构建通过
- **前后端必须同时验证**：改了后端必须检查前端调用是否适配；改了前端必须确认后端接口没变
- **行为等价验证**：插件化改造阶段，每轮改动必须确认用户可见行为不变。验证方式：跑现有测试 + 对比改动前后的 API 响应结构
- 里程碑完成后跑完整测试（后端 pytest，前端 vitest）
- 测试失败必须实证，禁止猜测归因

## 4. 多步任务先列计划（硬性要求）
- 超过 3 个文件的改动，先列出步骤计划，每步带验证点：`[步骤] → 验证: [检查方式]`
- 把命令式任务转化为可验证目标
- 计划中必须包含前端和后端的验证步骤

## 5. 调试排错（硬性要求）
- **最多猜 1 次**：修复 bug 可以快速尝试一次，无效立即加日志做科学排查，定位根因后再修

## 6. 高危操作
- 全量数据操作/脚本执行必须等用户确认；批量操作先测 5 个样本再全量

## 7. 知识库维护
- devlog / docs 可以按规则自动写；project-memory / 领域 knowledge 只有跨轮长期有效时才写
- **写入判断**：这条信息换个人接手还需要知道吗？
  - 写：架构决策、接口契约、Provider 设计约定、踩坑经验
  - 不写：bug 调试过程、临时 workaround、实现细节（看代码）、通用编程知识
- **状态覆写**：更新时直接修改旧内容，不保留矛盾的历史版本

## 8. 代码提交
- 里程碑完成后提交，提交前更新本轮任务对应的 TODO / 设计文档 / knowledge
- commit message 中文多行：第一行 `类型: 描述`，body 写变更要点
- 提交前核对文件列表，严禁提交 node_modules/venv/dist/__pycache__ 等
- 多 agent 并行时，只提交当前对话中由自己直接修改并完成验证的文件

## 9. 项目推进
- 按 V2 方案 Phase 顺序推进，每轮只做一个 Phase 的一个子任务
- 日常迭代用 TODO 驱动（`.kiro/docs/*-todo.md`）

## 10. 会话接力
- 修改后端 Python 或前端组件代码前，先读 project-memory.md 获取领域索引和核心红线
- 按需深入读取对应的 knowledge 文件
- 插件化改造时，必须先读 V2 方案确认当前 Phase 的目标和禁止事项

## 11. 插件化专属约束
- 新插件代码禁止 `from shared import xxx`，必须通过 ProviderContext 注入依赖
- Provider 只负责获取原始数据，评分/过滤/排序/下载决策属于 Core
- 所有跨层数据传递必须用 Pydantic DTO，禁止裸 dict
- Core 代码中不允许出现具体资源站名称（Bitsearch/Nyaa/蜜柑/1337x 等）
- 前端不允许新增硬编码 provider 列表，应从 `GET /api/providers` 获取
